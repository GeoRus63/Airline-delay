## 实际执行顺序

先用基础数据跑出第一版结果，再逐组扩展。天气与机型不是第一版模型的前置条件。

| 阶段 | 这轮增加什么 | 完成后应留下什么 |
|---|---|---|
| P0 最小可用分析 | 五个月航班清洗与衔接；4–7 月基础 EDA、RQ1 原始汇总、三个朴素基线和 G0 线性回归 | 第一版可运行结果、样本流、指标、图和问题清单 |
| P1 航班链 | G1：上游延误与飞机已完成航段历史 | 相对 G0 的同样本误差变化 |
| P2 机型 | G2：先 family，再单独比较 variant 粒度 | 两层机型是否有增益、未匹配情况 |
| P3 机场运行 | G3：事前可用的机场运行历史和计划负荷 | 动态运行信息的增量结果 |
| P4 天气 | G4a 实况 → G4b TAF → 单独试验 NOAA 补缺 | 三个独立对照、匹配覆盖及误差变化 |
| P5 完成开发分析 | 固定特征比较线性/树/森林；完成 RQ1 标准化、网络图和阈值敏感性 | 算法比较、因素解释、RQ1 完整开发期结果 |
| P6 冻结与最终评估 | 冻结候选及全部规则，评估 8 月；生成 4–8 月 RQ1 最终描述 | 最终测试结果与最终机场分析 |
| P7 报告与复现 | 整理研究演进、结论、图表和统一运行入口 | 中英文报告、汇报材料、证据索引与复现检查 |

每轮只改变一个研究因素：新增一组特征、改变机型粒度、替换模型、调整一项参数或改变数据规则，分别记录。修复影响结果的数据/时间错误时，先新建修正运行；此前相关结果标记失效并保留。

G0–G4b 累积链使用预定顺序、固定模型配置和相同评估样本，完整报告每一步，包括无增益的步骤。主线固定使用 family；variant 替换与 NOAA 补缺各作独立分支。之后可从当前最好版本做单独增加/移除试验，使用另一 run_id。增量大小与加入顺序有关，不能直接当作变量固有重要性。

## 每次运行如何留证据

### 只维护三处记录

| 位置 | 职责 |
|---|---|
| `research/研究记录.md` | 按时间追加“问题—依据—改动—观察—决定”，串起研究思路 |
| `experiments/index.csv` | 每次实际运行一行，列 run_id、parent_run_id、阶段、状态、改动、决定、结果目录 |
| `experiments/runs/<run_id>/` | 这次运行的实际配置、来源、结果、日志和图表；完成后保留原样 |

run_id 使用递增编号，如 `R0001`、`R0002`；parent_run_id 指明直接比较对象，第一轮留空。状态使用 `running/completed/failed/invalidated`。无增益是正常结果，不是运行失败。后来发现错误时，在索引和研究日志中标记 invalidated、说明原因并链接修正运行，原始输出不删改。重跑使用新编号。

### 一次正式运行的目录

| 文件 | 保存内容 |
|---|---|
| `config.json` | 本次实际使用的配置副本：阶段、特征列、模型/参数、预处理、样本规则、切分、种子 |
| `manifest.json` | Git 提交号、环境版本、原始输入哈希、派生数据版本/生成配置、样本量、运行命令、起止时间、状态、输出路径/哈希 |
| `metrics.csv` | 分折、分组和整体指标，含样本数与单位；RQ1 结果表也在该运行目录保存 |
| `evaluation_ids.csv.gz` | 每个验证/测试折实际使用的 connection_id，供公平比较与复核 |
| `figures/`、`notebooks/` | 本次图表和相应的已执行 Notebook；保留输出及解释 |
| `run.log` | 实际运行日志；失败时保留错误与已完成阶段 |
| `predictions/`、`models/` | 正式预测实验的完整预测明细和模型，避免后续覆盖 |

运行前先提交用于该实验的代码；运行后将研究记录、配置、日志、指标、关键图和已执行 Notebook 提交到 Git。不把配置不同或样本不同的 MAE 直接当成模型改善；配对比较核对 evaluation_ids 和切分哈希。派生数据规则改变时分配新 data_id，并保留其生成配置、源哈希、行数和样本定义；可重建的中间缓存不必每轮复制一份。

大体积预测、模型和派生数据保存在本机并登记路径与哈希，当前 `.gitignore` 不上传这些目录。原始数据、实验轻量证据和研究日志进入 Git。**完整运行产物的保存还包括这些本地大文件；再次迁移时需同步并校验它们。** 不因未纳入 Git 而删除旧实验。

研究日志每轮追加六项：要验证的问题、依据或前轮现象、唯一改动、实际结果及证据路径、保留/放弃/待验证的决定、下一步。文献驱动的改动同时记标题、页码/章节、借鉴的方法及本项目如何验证。

## P0：先得到第一版可用结果

按环境文档创建虚拟环境，并创建 `docs/执行进度.md` 记录当前阶段和下一步。以下 `python` 均指新环境解释器。

```bash
python scripts/verify_downloads.py
python scripts/prepare_flights.py --check
python scripts/prepare_flights.py
```

文件校验对应克隆时的交付快照，在编辑代码前执行。之后原始数据哈希仍作为输入依据，各实验保存自己的代码和运行版本。

现有 `notebooks/01_航班清洗与衔接.ipynb` 调用同一准备代码。全量运行时核对原始 3,057,590 行，保留原始行定位、取消/改道中断、重复与异常标志，处理当地时区、跨日和 `2400`。按同机计划顺序构造候选，再核验实际时序和机场连续性。生成：

- `processed/flights_clean.csv.gz`、`connection_candidates.csv.gz`、`flight_connections.csv.gz`。
- 样本流、排除原因、字段说明和能回溯原始行的核查实例。

首先实现基础版 `scripts/build_features.py`、`train_models.py`、`evaluate_models.py`；只产生 G0 所需列及评价字段。设 `prediction_time` 为上游实际到达、`label_time` 为下游实际出发、目标为下游非负出发延误。RQ2 使用标签可用且 prediction_time < label_time 的有效衔接，包含上游准点记录，隔夜衔接单列误差；不套用 RQ1 的至少 15 分钟筛选。

实现并执行 `03_EDA.ipynb`、`04_RQ1机场分析.ipynb`、`05_RQ2预测与解释.ipynb` 的基础部分，放在 `notebooks/`。先得到开发期分布、样本支持、上游延误 × 计划周转图、RQ1 原始机场汇总，以及训练均值/中位数/上游延误原样传递基线和 G0 线性回归。完整结果按 R0001 等运行编号归档。

## P1–P3：沿同一实现增加特征

按研究计划在 `build_features.py` 增加航班链、机型和机场运行计算，创建 `notebooks/02_天气与特征.ipynb` 展示生成与核对结果。

- P1 只使用预测前已完成的飞机历史；计划周转已属于 G0，不再重复计作新增变量。
- P2 运行已有 `python scripts/prepare_aircraft.py`，再实现映射到航班/衔接的连接。2024 清单作主参考、2025 作覆盖对照；family 与 variant 的粒度比较单独运行，线性模型避免嵌套类别共线。
- P3 计算机场过去 60 分钟已出发数量及平均延误、预测后 60 分钟计划进出港负荷；保留历史窗口不足标记与计划信息假设。

维护 `tables/feature_dictionary.csv`：含义、单位、来源、生成规则、可用时点、缺失处理和特征组。每轮归档字典版本、特征可用性检查和样本数量。开发比较仍使用同一模型和相同时间折。

## P4：天气逐步加入

现有天气准备入口：

```bash
python scripts/download_taf_text.py --prepare-validity
python scripts/prepare_weather.py
```

它们读取已下载的完整报文，生成 `references/taf_validity.csv` 及 `processed/` 中的实况、TAF 公告和分段表。逐航班天气连接与 NOAA 融合仍需实现。

先用 IEM 实况做 G4a 实验，再用当时可得 TAF 做 G4b，最后单独比较 NOAA 补缺前后。已下载的所有字段不必同时进入模型。关键要求：

- METAR 按观测后 5 分钟可用的假设连接，最大观测年龄 120 分钟，保留时间差、缺失和来源。
- TAF 先选预测时点已可用的最新公告，再在公告内匹配查询时刻；查询时刻为下游计划出发与 prediction_time 的较晚者。分别处理主导、TEMPO/概率段、修订、取消/NIL和有效期。
- IEM 为主源；NOAA 按官方质量码和单位核对重叠观测，再补充合格缺失值，并记录逐值来源。
- 缺天气不删除整条航班，也不填成晴天。先做同样本增量比较，再另报共同天气覆盖子集。

每轮保存天气匹配覆盖、时间可用性检查、源重叠核对和实际新增列；训练插补、编码与缩放只在各折训练段拟合。

## P5：完成开发比较与因素解释

所有模型使用统一的 4→5 月、4–5→6 月、4–6→7 月前向验证，UTC 月初半开区间，训练标签在各折截止前成熟。固定特征后比较线性回归、决策树、随机森林；有限参数候选与种子按研究计划执行，每个候选有独立 run_id。

保存 MAE/RMSE、样本数、普通/严重延误及机场/航司/机型分组误差；图示特征组增量、算法差异、残差、分组 permutation importance、系数和少数关键 PDP。结论写清改善是否稳定、哪些组无增益、误差仍集中在哪些场景。

用 `scripts/analyze_rq1.py` 完成机场共同支持标准化、日期块区间、网络图与 >0/≥5/≥15 阈值敏感性；使用同一分层集合和参考权重，保留支持率与可比机场清单。网络节点、边、累计分钟等定义统一采用研究计划。

## P6：冻结方案，使用最终测试集

将全部冻结候选、特征、预处理、阈值、参数、种子和选择理由存入该次运行的 `model_selection.json`，再用 4–7 月成熟标签重拟合，在 8 月 UTC 窗评估一次。冻结候选可以统一报告测试结果，不据此返回调参。随后完成 4–8 月 RQ1 最终描述；当地 8 月但跨出 UTC 主窗口的记录单列。

严格相同代码、配置和输入的复现运行可以重新计算并核对结果，使用新的 run_id。若查看 8 月后修改方法，标为测试后探索，不继续把 8 月当作未见测试集；正式再验证需要新的未见数据。

## 代码结构与统一入口

复用现有准备函数；Notebook 调用脚本计算，再展示结果与解释。新增特征改对应特征函数和配置列名，新增模型复用同一训练/评估函数与切分。项目设置使用一份简单 JSON，不引入插件注册、通用调度框架或外部实验管理服务。

在新电脑实现 `scripts/run_pipeline.py`，支持配置与唯一运行编号，按当前阶段执行必要工作。例如：

```bash
python scripts/run_pipeline.py --config configs/current.json --run-id R0001
```

入口和配置文件目前尚未实现。配置指定开发/最终阶段、特征组和模型；归档实际配置。阶段成功后保存输出，后续复用相同输入与规则的已完成准备步骤。最终使用冻结配置执行完整流程，另存复现运行，不覆盖原实验。

完成标准：分析已实际运行；数据与时间检查通过；RQ1/RQ2、全部必做增量和敏感性分析有结果；每个实验含正负结果都有记录；报告结论能追溯到有效运行；统一入口可重建结果。`docs/执行进度.md` 只记当前进展和下一步，研究依据以研究日志和运行归档为准。
